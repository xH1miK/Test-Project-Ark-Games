## Scope
Must: tractor + upgrade to tier 2 · balls scooped into the bucket and handed into the shredder (2 coins each) · arrow tutorial · basic sounds · gate opening = final point.
Plus: juice (coin flights, shredder rollers, upgrade swell, camera zoom-out, particles at the gate).
Out: intro flyover, packshot/CTA, second floor, gold balls, conveyor.

## Architecture
`assets/scripts/{core,input,camera,tractor,balls,world,economy,tutorial,audio,ui}`
- No physics module. Tractor, balls and pads use our own code (static XZ obstacle grid, custom ball sim).
- BallField is data-oriented (typed arrays, uniform grid, sleeping balls). BallRenderer draws all balls with one dynamic mesh = one draw call (impostor effect).
- All tunables in `core/Config.ts`. Systems talk through `core/Events.ts` where practical.
- Static level layout lives in the scene (built via MCP); dynamic objects are spawned by code.
- `core/GameRoot.ts` is the composition root: creates the models, injects them into views, runs the frame in a fixed order (input, then steps of ≤ `Config.time.maxStep`: tractor → bucket scoop → balls → bucket carry → shredder; then the coins in the air; `lateUpdate`: camera, renderers, rollers). Level collision = `StaticBlocker` components under the `Level` node → `ObstacleGrid`.
- Drive (M2): `JoystickModel` → `MoveInput` (camera-relative, autopilot override) → `TractorModel` (body circle `bodyOffset` ahead of the pivot, substeps ≤ `maxStep`) → `TractorView`; `CameraRigModel` (`zoomTo` on `tierChanged`) → `CameraRigView`; `UiFit` on the Canvas keeps the 1280×2276 frame on screen.
- Balls (M3): `BallField` (3D position-based; XZ cell grid, a column per cell; only balls in hot cells are simulated; order of authority in a step: floor → pusher → field edges → rocks, so rocks always win) + `layCarpet` (seeded). The tractor is the `BallPusher`: per-tier `pusher` boxes in its axes, faces shared by body and bucket are `shut`. `moved` lists balls a view must redraw. Tests/bench share `tools/test/ball-world.mjs` (fixture arena, autopilot, `measure`: "outside" = outside the flood-filled arena, not the edge rectangle).
- Ball rendering (M4): `BallQuads` (pure; per ball 4 vertices in two streams: dynamic = centre + radius float32 and orientation as an int16 quaternion, static = quad corner + shade bytes; `writeMoved` rewrites only `BallField.moved` and rolls them: turn about up × way by way / radius) → `BallRenderer` on node `Balls` (Default layer, at the origin) owns a render-scene `Model` (not a MeshRenderer: the dynamic stream is a HOST|DEVICE buffer, uploaded once per frame only if something moved) → `assets/effects/BallImpostor.effect` (quad facing the eye, sphere ray-traced in the fragment shader, `gl_FragDepth` / `EXT_frag_depth` in WebGL 1). One sub-model, one pass = 1 draw call. The look lives in the effect's property defaults; `Materials/Balls.mtl` overrides nothing. GameRoot calls `ballView.render(balls, bucket)` in `lateUpdate` before `balls.clearMoved()` / `bucket.clearMoved()`.
- Bucket (M5): a scooped ball keeps its index — `BallField.hold(i)` takes it out of the grid (not simulated, nobody's neighbour), its holder moves it with `place`, `release` puts it back; `findFree(rect)` queries the grid. No repacking, so views key per-ball data by index; `field.x/y/z` always says where every ball is. `Bucket` (pure, `tractor/`): intake = the tier's `bucket` cavity (tractor axes, measured on the mesh) + one radius ahead; `scoop()` before the field steps takes free balls in the intake while there is room (90% of their speed relative to the tractor, `ballScooped` event); the bucket's pusher box stays solid (as high as a full heap), so what is in front is taken before the box could shove it and a full bucket pushes like a blade. `carry(dt)` after the step: `BucketLoad` (pure) settles the pile in the bucket's axes (all pairs, cavity walls, a shrinking slack draws a ball in from the lip, a mound above rim + `heapLayers`, `contactSlop` 0.1 keeps it compact like the example's, asleep `settleTime` after the last take) and places the balls in the world. Follows the tractor's tier (`bucketShape`/`bucketCapacity`); `unloadAll(out)` hands the load over (M6: the balls stay held where they are). `BallQuads.writeCarried` is the second write path: carried balls turn with the carrier's yaw and roll only along their way inside it; `writeMoved` lets a ball back in the field roll on from where it is. `measureLoad` in `ball-world.mjs` audits the load.
- Shredder and coins (M6, `economy/`): `BallField.moveHeld` moves a held ball and lists it in `moved` (drawn as a loose ball; `place` is for a carrier that draws it itself); `remove(i)` takes a ball out of the game for good (stays held, `removed[i]`, listed once; `BallQuads` writes radius 0 — no repacking, still 1 draw call). `BallFlights` (pure, `balls/`): lerp + sin(πt)·arc, `remove` on landing. `Shredder` (pure; pose from the `Level/Shredder` node): while the tractor's body (the centre of its collision circle, `bodyX/bodyZ` — since M9: a long machine's pivot stays far from the shredder it bumps into) is in the ±`zoneHalf` square (world axes) `bucket.unloadAll` → every ball flies 0.32·(1..1.4) s to the top ± 0.6; the throat = a box in the shredder's axes (`findFree` over its cells, not a scan) → held → 0.16 s into the mouth; landed balls pay per step (`ballsShredded`, `coinsEarned` at the shredder top); rollers ramp (speed share + angle). While in the zone the bucket keeps scooping and every step's scoops go in too. `CoinFlights` (pure): a payout = ≤ `spritesPerPayout` coins sharing it, ≤ `maxAlive` in the air (full sky: credited at once), each credited to `Purse` on arrival — the juice-stage sprites will draw `coins[0..count)` by `time/duration`. `Purse` → `purseChanged` → `CoinHud` (`ui/`, retriggerable punch in `update`). `ShredderView` turns `roll_*` (top toward the middle). Invariant the scenarios check: purse + coins in the air (+ coins on the pay pads, M8) = 2 × shredded; held = carried + flying + removed.
- Pay pads (M8, `economy/`): `PayPace` (pure; the first coin at once, then one per `interval`, speeding up evenly so the whole remaining price leaves the purse within `fillTime`; its clock runs only while paying). `PayPad` (pure; zone ±`zoneHalf` round its spot, world axes): takes from the purse only while the tractor's pivot is in the zone, the pad open (shown, not closed, unpaid) and the purse not empty; the coins fly through the pad's own `CoinFlights` (the pad is the receiver — the juice-stage sprites get them for free) and count on landing: `owed` = price − landed is what the counter reads; a partial payment stays; leaving the zone stops the pace (the next visit starts with a coin at once); `coinsSpent` per take, `padPaid` once. `Progression` (pure): the gate pad is shown from the start; the upgrade pad hides until the first `loadHandedIn` (a bucket hand-in; throat balls do not count), then `show()` + `BallField.burst` (r 2.8, 14 u/s, from the example); a paid upgrade pad closes (reads MAX) and calls `machine.setTier(tier + 1)` (`Upgradable`, M9); the gate pad ends the run (M10, below). Clear zones (`BallField.addClearZone`, a pad's `clearZone` = plate + `clearMargin`, active while the pad is open): a floor ball (y < 1.5 r) whose centre is inside is moved toward the nearest edge with room for a ball beyond it (no wall within a diameter behind it — the gate plate's south edge is 0.48 short of the gate: balls pinned against the gate kept one in the zone for ever, awake) by at least `clearSpeed`·dt per step, in the hard limits **before** the pusher (the tractor wins and can shove balls onto a plate; a speed instead of a move made the ball ride up onto the crowd outside and never leave); a ball up on the crowd outside only overhangs the margin; a zone turning on wakes its balls; a floor ball on a live zone stays awake. `PayPadView` (on the spot node; also the gate's price sign, same model): `visual` = a RenderRoot2D child lying flat (rot −90 X) or standing, with a sprite and a `hud-digits` counter (digits + MAX), both on `Materials/WorldSprite.mtl` (builtin sprite with depth test on, no depth write: the tractor and the balls draw over the plate) — one draw call per plate/sign (sprite and glyphs share the dynamic atlas); pop `popTime` backOut / shrink `shrinkTime` backIn; `plateRect(margin)` gives the plate's world XZ rect. GameRoot: the gate plate's clear zone is a hole in the carpet (shrunk by a radius: a hole keeps centres a radius off its edge); pads step after the coins in the air (`progression.step(frame)`).
- Upgrade (M9): `TractorModel` holds every tier's stats and a 1-based `tier`; `setTier(n)` (clamped) announces `tierChanged` itself, so a QA `setTier(2)` also zooms the camera and swaps the model. A bigger body that arrives overlapping an obstacle grows into its size: the collision radius less a grace that shrinks to 0 over `Config.tractor.swell.time` (no 1-unit jump next to the shredder). `TractorView.models` = the tier models, tier 1 first (`Tractor/Tier1` = the linked Tractor1.glb instance, its duplicate track nodes `Tire2`/`Tire3` switched off by overrides — all three drew the same mesh at the same place; `Tractor/Tier2` = an unlinked copy of Tractor2.glb at scale 1.2 as in the example, inactive at start, on Tractor1's materials and zombie/track meshes); the view shows the model's tier every frame and swells a newly reached one `swell.from` → 1 over `swell.time` (backOut tween), the first render without it. T2's cavity, boxes and `bodyOffset` were measured on its mesh (`tools/measure-tractor.mjs`); `BucketShape.backRound` rounds the floor–back edge (a ball is held off it horizontally: a closest-point push is a ramp that throws balls thrown in back out). T2's body is 1.8 (GDD) with `bodyOffset` 0.97: its teeth reach 0.55 past the circle (T1: 0.12); a larger radius would keep the body out of the shredder's ±3.5 zone.
- Gate and finale (M10): paying the gate pad ends the run. `Progression` on `padPaid` 'gate': `controls.lock()`, `gatePad.hide()` (hide, not close: the shrinking plate and sign read 0, not MAX), `gate.open()`, in that order (a test checks it). GameRoot's `controls` = `MoveInput.lock()` — **the one place that zeroes the drive command**, for the joystick and an autopilot alike (`setFromStick`/`override` do nothing once locked; the tractor brakes at `brake`, T1 stops within 0.3 units) — plus `JoystickModel.disable()` (lets go of the finger, ignores new touches, `visibility` fades to exactly 0 for the view's opacity). `Gate` (`world/`, pure): closed → opening (`Config.gate.openTime` 0.85 s) → open; `progress`, `fold` (0 during the 15% hold, then a smoothstep), `flash` = sin(π·progress); announces `gateOpening` in the payment frame (audio/FX/finale listen) and `gateOpened` once. GameRoot steps the gate **before** the pads, so a gate opened by this frame's payment starts counting next frame (the event gap is then ≥ 0.85 s at any FPS). `GateView` = the force-field curtain: `Level/GateCurtain` (RenderRoot2D, scale 0.01, at (1.17, 0, −14.6): the doorway measured on the mesh — posts' inner edges x −1.36..3.70, lintel 3.3–3.5, posts' faces z −14.22..−15.07) with sprite children `Sheet` and `Sparks` (520×350 UI units, anchored bottom-centre, `WorldSprite.mtl`, textures from `tools/art/procedural.mjs`); sealed = shimmer alpha 0.9–1.0; opening = sheet scale Y 1−fold and raised `height·fold` (its top stays under the lintel) while it fades, sparks alpha = flash and drifting up; open = node inactive; 1 draw call while it stands. `FinaleView` (`ui/`, `Canvas/Hud/Finale`, the last child of Hud): `Title` = bitmap-font Label `assets/fonts/finale-title` ("GATE OPEN!", gold gradient with a purple outline, baked by `tools/art/font.mjs`) pops with backOut at `Config.finale.title.height` (0.26) of the screen height above the middle and pulses ×1.05; `Pieces` = 64 pooled Sprite nodes (`confetti.png` tinted per piece, made at the first `play()`) driven by `fx/Confetti` (pure: 60% fired from the bottom corners, the rest rains over `rainDelay`; UI units of the Hud's UITransform, so it fills a portrait or a landscape screen). GameRoot calls `finaleView.play()` on `gateOpening`. The whole finale is in the UI's one batch: 0 extra draw calls. **Scenario routes must not pay the gate**: `sweepFrame(shredder, zoneHalf, gatePad, padZoneHalf)` adds an `avoid` square (the pad's zone + 0.8) that no fill-up target may lie in or be reached across, and `checkLoopProbe` asserts the gate stayed shut with the controls on; a route that starts at (3, −11) is inside the zone but the purse there is 0.
- Tutorial (M11, `tutorial/`): `TutorialFlow` (pure) — steps `off → sell → upgrade → gate → done`, `begin()` starts it, `update()` recomputes the step and the target **every frame** from the world (GameRoot calls it last in `update`, after `progression.step`, so a gate paid this frame is Done this frame): upgrade pad shown → `upgrade`; upgrade pad closed or `tier ≥ maxTier` → `gate`; gate phase ≠ closed (or the gate pad hidden/closed) → `done`; it only ever moves forward. `target` = one of three preallocated points (`shredder` | `upgrade` | `gate`, world XZ) or null. `aimPad`: **purse total 0 and the pad's `missing` (price − landed − in the air) > 0 → the shredder**; any coin in the purse → the pad (even when it needs more than there is, as in the example); coins already flying to the pad are not needed any more (they are out of `missing`). `TutorialMarkers` (pure): the path arrow floats `forward` 3.2 ahead of the tractor's pivot along its own yaw at height 1.5 and swings to the target at ≤ 540°/s by the short way round (it snaps when it first appears or reappears, and keeps its heading while the target is under the pivot); the pointer stands over the target (height 3 over the shredder, 2.5 over a pad) and bobs ±0.15 with period 1.1 s (an honest clock: same at any FPS; it restarts on a new target); a null target hides both. `ArrowGeometry` (pure): the shape is built in code (16-segment shaft + cone, tail at the origin, tip forward: 113 vertices, 96 triangles, proportions of the example's fallback arrow) — no model asset, and no `primitive` engine module (it is off in the build; `utils.MeshUtils.createMesh` is enough). `TutorialView` on the top-level node `Tutorial` (at the origin, identity): one mesh, one runtime `builtin-standard` material (albedo (60,255,80) as the example, roughness 0.9), **`USE_INSTANCING`: both markers = ONE draw call** (a device without `ANGLE_instanced_arrays` draws two: checked with `--hide-ext`), nodes `PathArrow` and `Pointer` with a MeshRenderer each on the Default layer, no shadows; the pointer is tipped 60° nose down and turned to the camera's yaw (leans over towards the viewer). World objects of the main camera, not Canvas: the screen-UI rule does not concern them. `Material.initialize({ effectName: 'builtin-standard' })` needs that effect in the build: it is there because the tractor's materials use it — if they ever change, the arrow breaks (the `tutorial` scenario looks at the pixels). The look and numbers (`Config.tutorial`: colour, scales 1.4 / 1.54, pitch, heights) were picked by the user from three variants (3D arrow from code / flat "cartoon" extruded chevron / sprites) on 29.09.
- Full run (M12; tools only, the game did not change): `fullRun` (`tools/test/ball-world.mjs`) plays the whole game on the pure models the way a careful player would, **no coin from outside**: T1 rounds (`roundLegs`, long-run's fill policy) until the purse — with the coins still in the air — holds what the upgrade pad lacks → `upgradeLegs` onto it → T2 rounds → the same test for the gate pad → `gateLegs` (`lib/sweep.mjs`: straight on from south of the shredder, else round it on the tractor's side and down that side to z −8; then onto the pad, standing until the condition `gateOpen`) → frames until the gate is open. It returns the game time and state at each event (`marks`: firstScoop, firstHandIn, upgradePad, firstCoins, upgradePayStart, tier2, upgradePaid, gatePayStart, gatePaid, gateOpening, gateOpened). Result at 10–60 fps: 18–23 s of game time, 5–7 rounds (3–4 of 8, then 2 of 60), ~300 of 1446 balls shredded (a fifth of them through the throat), ~620–660 coins earned for 400 spent. `tools/bench/full-run.mjs` prints it; `tools/test/full-run.test.mjs` runs it at 60 / 30 / 15 fps with a real `TutorialFlow` and the wallet ledger checked on every frame. The autopilot's `full` condition compares with the tractor's tier (`bucket.count >= tractor.bucketCapacity`): the bucket follows a new tier on its **next** step, so `bucket.full` read right after `tierChanged` still had the old capacity (a fill leg started after the upgrade ended at once with 8 of 60).
- **Screen UI is always on top** (user rule, 28.09): all of it lives under `Canvas`, drawn by the Canvas' UI camera — priority above every other camera, clears depth only, sees `UI_2D` only. Groups in draw order (a later sibling is drawn on top): `Canvas/Hud` (HUD: `CoinHud` › `Plate` (sliced) › `Icon`, `Amount`; later buttons, coin flights, tutorial texts, end screen) → `Canvas/Joystick` (last = topmost). The whole screen UI is one batch: its sprites go into the engine's dynamic atlas and numbers use bitmap fonts (`Amount` = `assets/fonts/hud-digits`, packed once). A system-font Label costs +2 draw calls (its own texture splits the batch) and a new texture on every change; its BITMAP cache mode clogs the atlas (`hud-atlas` scenario, M7) — never use either for text that changes. New UI goes into a group, never straight under `Canvas`; no 3D node on `UI_2D`, no camera after the UI camera; world-space UI (the pad plates and the gate sign: RenderRoot2D on the Default layer with `WorldSprite.mtl`) is drawn by the main camera. The `drive` scenario checks all of it (`tools/scenarios/lib/ui-layers.mjs`).
- QA hooks: with `?qa` in the URL the models are published on `window.__zm` (`core/QaBridge.ts`) for scenario scripts.

## Code style (the user asked for MVP, OOP, SOLID)
- **Model** = plain TypeScript without `cc` imports: game state and rules, unit-tested in Node. **View** = Cocos component that only renders/applies state. **Presenter/controller** = wires a model to its views.
- One responsibility per class; dependencies passed in by the composition root, no hidden singletons (Config and the event bus type are the shared vocabulary).
- Pure modules use erasable TS only (Node type stripping): no `enum`, `namespace`, parameter properties; `import type` for types; extensionless relative imports.
- Checks: `node tools/typecheck.mjs` (strict tsc bundled with Cocos) and `node --import ./tools/test/register.mjs --test "tools/test/*.test.mjs"`.

## Cocos 3.8.8 conventions
- `import { _decorator, Component, Node, Vec3 } from 'cc'; const { ccclass, property } = _decorator;` with a project-unique `@ccclass('Name')`.
- Lifecycle: onLoad → onEnable → start → update(dt) → lateUpdate(dt) → onDisable → onDestroy.
- Right-handed, Y-up, cameras look down −Z. Position/rotation getters return readonly refs — use setPosition / setWorldPosition / setRotationFromEuler.
- No allocations in per-frame code: reuse module-level temp Vec3/Quat, prefer `Vec3.add(out, a, b)` statics.
- Motion via `tween()`, timers via `scheduleOnce`. Stop a node's tweens with `Tween.stopAllByTarget(node)`: `tween(node).stop()` makes a new, empty tween and stops nothing. A tween started in `lateUpdate` takes its first step next frame, and that step counts as 0 (engine `action-interval.ts`). AudioSource has no pitch → use clip variants.
- Runtime-loaded assets must live under `assets/resources`.

## Editor & MCP rules
- MCP server `cocos` = Funplay Cocos MCP v0.6.4 (`extensions/funplay-cocos-mcp`, gitignored; install steps in `docs/SETUP.md`), `http://127.0.0.1:25720/`, `full` tool profile (`funplay-cocos-mcp.config.json`). It runs inside the editor: if its tools fail, ask the user to open the project in Cocos Creator 3.8.8. Health check: `GET http://127.0.0.1:25720/health`. If the session started before the editor, its `cocos` tools stay unloaded until the user reconnects in `/mcp` — meanwhile call them with `node tools/mcp.mjs <tool> '<json>'` / `node tools/mcp.mjs js <scene|editor> @file.js`.
- Change `.scene` / `.prefab` ONLY through the Cocos MCP or the editor. Never hand-edit scene/prefab JSON; never edit or copy `.meta` UUIDs.
- **asset-db URLs are case-sensitive, the Windows file system is not.** Use the exact case of existing folders (`db://assets/Materials/...`, capital M — made by the FBX import). A wrong-case URL makes asset-db register the folder twice and re-UUID its files (happened 27.09; fixed by restoring the metas from git and a clean re-import).
- New assets from code: create in the scene process and serialize with `EditorExtends.serialize`, then `asset-db create-asset`/`save-asset`. For materials strip pipeline macros (`CC_*`) from `_defines` — the serializer bakes the editor's pipeline state into them.
- **Never call the MCP `refresh_assets` without a path**: it refreshes `db://assets/` (trailing slash) and asset-db registers a phantom folder for the assets root (`assets/.meta`, happened 27.09). Refresh exact files: `Editor.Message.request('asset-db', 'refresh-asset', 'db://assets/scripts/x.ts')`. Never `delete-asset`/`move-asset` a folder whose source is the assets root.
- Linked prefab instance: `scene:create-node` with `{ parent, assetUuid, type: 'cc.Prefab', unlinkPrefab: false }` (without `type` it comes out unlinked). Change instance children through `scene:set-property` — that records a prefab override; a raw scene-script change does not. The MCP tool `inspect_prefab_instance` can return megabytes — check `node._prefab.instance` in a scene script instead. A linked instance is rebuilt from its prefab asset at runtime, so the build packs that prefab with everything it references — overrides only add references: to reuse another model's materials or meshes, use an unlinked copy (`unlinkPrefab: true`, or `scene:unlink-prefab` after setting the overrides: they are baked into the nodes). `Tractor/Tier2`: linked with overrides +985 KB, unlinked +75 KB (M9). A glb prefab's root wraps the glb's own root node: zero that child's offset too (as Tier1's override does).
- A reference from outside a prefab instance to a node inside it (`ShredderView.rollers` → `roll_*` of the SM_Shred FBX instance) goes through `scene:set-property` (array dump `{ type: 'cc.Node', isArray: true, value: [{ type: 'cc.Node', value: { uuid } }] }`): the scene stores it as `targetOverrides` on its prefab info. Check a save with a structural diff of the `.scene` (objects keyed by node path + component type), not the raw diff — new objects renumber every `__id__` after them: `node tools/scene-diff.mjs [file] [rev = HEAD]`.
- Adding a `Label` to a node resets its UITransform size (a SHRINK label then shrinks its font to the default box): in a scene script set the size after adding the Label, or through `scene:set-property` (`__comps__.<i>.contentSize` = `{ type: 'cc.Size', value: { width, height } }`).
- UI built from a scene script: set Widget margins last and through `scene:set-property` (`__comps__.<i>.top` …). Resizing a Widget node in the editor makes its "stay put" logic rewrite the margins (a stretched node got −1088/−590 on 27.09). UI nodes need `layer = UI_2D`; start a Canvas from the editor preset `db://internal/default_prefab/ui/Canvas.prefab` (`unlinkPrefab: true`) to get its UI camera.
- `git commit` before any batch of scene operations; save the scene through MCP afterwards.
- A new `.ts` file must be compiled by the editor before its component can be added — wait for the asset refresh.
- After each feature: run the preview in the browser, check the console, drive the tractor with a scripted autopilot (override the joystick output via JS) through the scenario, take screenshots.
- Milestone check from `file://` (user wish, 28.09: a full batch took 1.5 h): every scenario on the GPU; on SwiftShader (~4 fps) only the milestone's own scenario and those its change touches, `long-run` quick (`ZM_LONG_SHARES=0.1,0.2`). `hud-atlas` and the full `long-run` on SwiftShader only when the HUD or performance changed, and once at the end of a stage.
- **Be gentle with the user's laptop** (29.09: it froze with 219 headless Edge processes, 12 GB, left by earlier runs, and had to be hard-rebooted): heavy jobs one at a time, never a build and a check together; SwiftShader runs with `ZM_AFFINITY=0xFF000` (the i7-13700H's 8 efficient cores — quiet, still ~9–10 fps) and a pause between runs. `tools/lib/browser.mjs` closes the whole browser instance after a run (DevTools `Browser.close`, then every process that names its `zm-check-` profile), kills strays of earlier runs at start, runs the browser below normal priority and refuses to start one with < 1.5 GB free. After a batch no `zm-check-` Edge process may remain; if commands start timing out, stop and look instead of queueing more. `tools/run-batch.sh <out-dir> <gpu|sw> <scenario>...` runs scenarios one at a time with a pause and counts the leftover `zm-check-` processes at the end (run it in the background and poll its log).

## Build
- `node tools/build.mjs` — web-mobile build inside the open editor (builder `add-task` via MCP) from `build-config/web-mobile.json`: Debug / source maps / MD5 off, Merge All JSON, mangle + inline enums. CLI build only with the editor closed (EPERM otherwise).
- Feature Cropping (`settings/v2/packages/engine.json`; change through `Editor.Profile`, not by hand while the editor is open): base, gfx-webgl, 3d, 2d, ui, audio, tween, legacy-pipeline. Add a module only when code needs it, then re-measure.
- `node tools/pack/pack.mjs` → `dist/ZombieMiner.html` + size report (hard limit 5,000,000 bytes, target ≤ 4.8 MB; empty scene = 0.56 MB).
- `node tools/check-html.mjs dist/ZombieMiner.html` — headless Edge from `file://`, portrait + landscape: zero external requests, no console errors, scene running; screenshots in `dist/shots/`. `--scenario <name>` runs `tools/scenarios/<name>.mjs` (adds `?qa`); an http target (`http://localhost:7456/`, the editor preview) is quicker while iterating; `--gpu` uses the real GPU for FPS numbers (default SwiftShader is software GL: deterministic, but slow on big PBR surfaces). Pages run as touch phones (DPR 2, touch emulation); scenarios get `t.touch(type, x, y)` for real touches, `t.heap()` (live JS heap after a full GC, through CDP) and `t.heapSnapshot()` (a heap snapshot summed up by kind of object). The headless browser launch lives in `tools/lib/browser.mjs` (shared with the art tools). In the build the engine's private fields are mangled (`_atlases` …): page scripts use public API only. ## Art
- `node tools/art/prepare.mjs [name] [--preview <dir>]` — resize/compress `art-src/` (GPT-image) into `assets/` with sharp (`cd tools/art && npm install` once). Specs live in the script (crop `circle` for round sprites, `trim` + `height` for panels such as the coin plate, drawn sliced). New images: exact-path `refresh-asset`, then set `userData.type = 'sprite-frame'` through `save-asset-meta` (what the Inspector does) and reimport; slice borders live in the `f9941` sub-meta.
- `node tools/art/font.mjs [name]` — bitmap fonts (specs in the script): glyphs drawn with the headless browser's canvas the way a Label draws (outline stroked twice its width, round joins, fill over it), 4× supersampled (headless canvas text has no antialiasing) → palette PNG + AngelCode text `.fnt` (imported as `cc.BitmapFont`, texture linked by the page name). The page must stay ≤ 512 px (larger frames are not packed into the dynamic atlas); set the page's sprite frame `trimType: 'none'`. Assign with `scene:set-property` `__comps__.<i>.font` = `{ type: 'cc.BitmapFont', value: { uuid } }` (the setter turns the system font off).

## Git
Small focused commits. Private GitHub repo (xH1miK). Never commit build/, library/, temp/, local/, profiles/, reference/.
- One branch per milestone/task from `main`: `<stage>/m<N>-<name>` (e.g. `core/m2-drive`).
- Merge into `main` only after the milestone is verified: `node tools/merge.mjs` — a `--no-ff` merge commit made without touching the working tree (the editor keeps the project open), then HEAD is on `main`; start the next branch with `git switch -c`.
- Roll back a milestone with `git revert -m 1 <merge>`; never reset `main` without the user's OK.
- Push (main and branches) only when the user asks.
